# Foxy 26.1 port, with a Sodium 0.9 compatibility layer for Voxy 0.2.16

Date: 2026-07-24
Status: approved, ready for implementation planning

## Goal

Run Voxy on a Minecraft 26.1.2 / NeoForge 26.1.2.84 instance that keeps **Sodium 0.9.1**,
without Sinytra Connector.

Two problems stand between here and there. Foxy already solves the first for 26.2; the
second is new and is the bulk of this work.

## Background: why not Connector, and why not just downgrade Sodium

**Connector is a dead end on this pack.** Forgified Fabric API's Indigo stands down whenever
any loaded mod declares the custom key `fabric-renderer-api-v1:contains_renderer`
(`IndigoMixinConfigPlugin.loadIfNeeded` checks key *presence*, not value). `sodium-neoforge`
declares it in `META-INF/neoforge.mods.toml` but ships no FRAPI implementation — the only
FRAPI class in the jar is `FRAPIProvider`, a `Services.loadOr` stub with no
`META-INF/services` entry, so it is a no-op on NeoForge. Nothing registers a `Renderer`, and
the first world render throws:

```
UnsupportedOperationException: Attempted to retrieve active rendering plug-in before one was registered.
  at RendererManager.getRenderer  [forgified-fabric-api.fabric-renderer-api-v1-13.0.8]
  at BlockFeatureRenderer.handler$...$beforeInitBlockRenderer
```

Sodium 0.8.12 declares the same key, so this is not fixed by downgrading. Foxy avoids it
entirely by never putting FRAPI in the game.

**Downgrading Sodium to 0.8.12 was the approved fallback and is rejected in favour of this
design.** It works — 0.8.12 has exactly the signatures Voxy 0.2.16 injects into — but it
forces `iris` 1.11.2 → 1.10.9, removal of `sodium-extra` (every 26.1.2 build requires sodium
`[0.9.1-beta.2,)`), and `reeses-sodium-options` 2.2.3 → 2.1.0. Keeping Sodium 0.9.1 keeps
that whole stack current.

## Part 1 — Shared source layout

The 26.1 and 26.2 modules share ~2,150 of ~2,170 lines. Rather than copying the tree:

```

                    FoxyDependencyLocator, FoxyEntrypoints, FoxyFabricApi,

                    AccessWidenerData
    fabricstub/     all stubs
```

Root `build.gradle.kts` adds the shared directory to every module:

```kotlin
subprojects {
    sourceSets["main"].java.srcDir(rootProject.file("common/src/main/java"))
}
```

The existing `exclude("net/fabricmc/**")` jar rule stays as-is.

### The two version deltas

Everything Foxy touches is identical between Voxy 0.2.16 and 0.2.18 and between NeoForge
26.1.2.84 (FML 11.0.15) and 26.2.0.28-beta (FML 11.0.13) — verified class-by-class for the
FML SPI surface, `VoxyCommon`, `ImportManager`, `WorldImporter`, `DHImporter`, `DebugUtils`
and `DebugEntries`. Exactly two things differ:

| | 26.2 | 26.1.2 |
|---|---|---|
| render-system holder interface | `IVoxyRenderSystemHolder` | `IGetVoxyRenderSystem` (renamed; same methods) |
| receiver of `allChanged()` | `Minecraft.levelExtractor` | `Minecraft.levelRenderer` (`levelExtractor` does not exist) |

Both hide behind:

```java
public interface VoxyCompat {
    void shutdownRenderer(LevelRenderer levelRenderer);
    void markAllChanged(Minecraft minecraft);
    static VoxyCompat get() { /* ServiceLoader */ }
}
```

`FoxyCommands.reloadInstance` calls through it instead of casting directly.

The Chunky mixin stays 26.2-only: it needs `org.popcraft.chunky.platform.NeoForgeWorld` on
the compile classpath and there is no Chunky in the 26.1 pack. `foxy.mixins.json` is already
a per-version resource, so 26.1's simply lists the Part 2 mixins instead.

`foxy-extra.accesswidener` copies over unchanged — `DebugScreenEntries.register(Identifier,
DebugScreenEntry)` exists in 26.1.2 with that exact descriptor and is private.

## Part 2 — Sodium 0.9 compatibility for Voxy 0.2.16

Voxy 0.2.16 targets Sodium 0.8.x. Its `fabric.mod.json` pins `sodium` to `0.8.9`–`0.8.12`,
and Foxy's generated `neoforge.mods.toml` already drops version ranges (`versionRange = "*"`),
so the pin is not what blocks loading — the mixins are.

Voxy has six Sodium mixins. Three are unaffected by 0.9 and are left alone:

- `AccessorChunkTracker` — `chunkStatus : Long2IntOpenHashMap` still present
- `AccessorSodiumWorldRenderer` — `renderSectionManager` field still present
- `MixinChunkJobQueue` — `<init>`/`new Semaphore(int)` and `shutdown` unchanged
- `MixinSodiumWorldRenderer` — `initRenderer` unchanged

Three break. Each is handled differently.

### Break C — `RenderRegionManager.uploadResults` gained a parameter

```
0.8.12  private void uploadResults(CommandList, RenderRegion, Collection)
0.9.1   private void uploadResults(CommandList, RenderRegion, Collection, UniformBufferManager)
```

Voxy's `@Redirect` pins the explicit 3-arg descriptor, so it fails to resolve and — with
`"required": true` and `defaultRequire: 1` — takes the whole mixin config down.

**Fix:** rewrite the annotation string in Voxy's jar. Foxy already rewrites Voxy's class
bytecode (`FoxyFabricModReader.remapFabricRefs`), so this is an ASM annotation-value edit in
the same pass: append `Lnet/caffeinemc/mods/sodium/client/render/chunk/UniformBufferManager;`
to the `method` descriptor. The redirect only wraps `Math.toIntExact(long)` and is
semantically inert, so no behavioural change is needed.

### Break B — `ShaderChunkRenderer.begin` gained two parameters

```
0.8.12  protected void begin(TerrainRenderPass, FogParameters, GpuSampler)
0.9.1   protected void begin(TerrainRenderPass, FogParameters, GpuSampler, GpuBufferSlice, GlTexelBuffer)
```

Voxy's `MixinDefaultChunkRenderer` calls the 3-arg form from its own `doRender` method. The
`@Inject`s on `render` are unaffected (both match by name; the `end(TerrainRenderPass)`
target is unchanged), so this surfaces at runtime as `NoSuchMethodError`, not at apply time.

**Fix:** the two new values are *available* — 0.9's
`DefaultChunkRenderer.render(ChunkRenderMatrices, CommandList, ChunkRenderListIterable,
TerrainRenderPass, CameraTransform, FogParameters, boolean, GpuSampler, GpuBufferSlice,
GlTexelBuffer)` receives both. A Foxy mixin on `DefaultChunkRenderer`:

1. `@Inject(method = "render", at = @At("HEAD"))` captures the `GpuBufferSlice` and
   `GlTexelBuffer` arguments into instance fields.
2. `@Redirect` on the `begin(TerrainRenderPass, FogParameters, GpuSampler)` invocation inside
   `doRender`, forwarding to the real 5-arg `begin` with the captured values.

Nothing is fabricated; Sodium receives exactly the buffers it passed in.

### Break A — `RenderSection.setInfo` changed return type

```
0.8.12  public boolean setInfo(BuiltSectionInfo)   // "did anything change"
0.9.1   public int     setInfo(BuiltSectionInfo)   // bitmask
```

In 0.9 the `int` is a bitmask: bit 0 = section flags or visibility data changed, bit 1 =
section has culled block entities or animated sprites. `RenderSectionManager.updateSectionInfo`
feeds it into `renderableSectionTree` membership (`RemovableMultiForest.add`/`remove`) and
`sectionsWithGlobalEntities`.

Voxy's `@Redirect` handler `voxy$updateOnUpload` replaces the `setInfo` call. It calls the
original but **never returns its value** — it only tests it, then returns a synthesized
`true`/`false`. Passed through to 0.9 unchanged, it would return `1` on every non-trivial
path and bit 1 would never be set. Animated sprites would never register for ticking and
culled block-entity tracking would be wrong — silently, with no crash and no log line.

This is the one break that cannot be fixed by rewriting descriptors.

**Fix:** replace the handler. Foxy strips the `@Redirect` annotation from
`voxy$updateOnUpload` in the same ASM pass as Break C, leaving it as an inert unused private
method, and supplies its own `@Redirect` on the same call site with the return type corrected.

The reconstructed 0.8 handler (decompiled from `MixinRenderSectionManager`) is:

```java
private boolean voxy$updateOnUpload(RenderSection section, BuiltSectionInfo info) {
    boolean hadFlags = section.getFlags() != 0;
    int flags = section.getFlags();
    if (!section.setInfo(info)) return false;
    if (hadFlags == (section.getFlags() != 0)) return true;
    flags |= section.getFlags();
    if (flags == 0) return true;

    VoxyRenderSystem rs = ((IGetVoxyRenderSystem) level.levelRenderer).voxy$getRenderSystem();
    if (rs == null) return true;

    int cx = section.getChunkX(), cy = section.getChunkY(), cz = section.getChunkZ();

    if (hadFlags && VoxyConfig.CONFIG.ingestEnabled) {
        Long2IntOpenHashMap chunkStatus =
                ((AccessorChunkTracker) ChunkTrackerHolder.get(level)).getChunkStatus();
        long pos = ChunkPos.pack(cx, cz);
        if (pos != cachedChunkPos) {
            cachedChunkPos = pos;
            cachedChunkStatus = chunkStatus.getOrDefault(pos, 0);
        }
        if (cachedChunkStatus == 3) {
            LevelChunk chunk = level.getChunkSource().getChunk(cx, cz, ChunkStatus.FULL, false);
            if (chunk != null) {
                LevelChunkSection sec = chunk.getSection(cy - bottomSectionY);
                LevelLightEngine light = level.getLightEngine();
                SectionPos sp = SectionPos.of(cx, cy, cz);
                DataLayer bl = light.getLayerListener(LightLayer.BLOCK).getDataLayerData(sp);
                DataLayer sl = light.getLayerListener(LightLayer.SKY).getDataLayerData(sp);
                VoxelIngestService.rawIngest(rs.getEngine(), sec, cx, cy, cz,
                        bl == null ? null : bl.copy(), sl == null ? null : sl.copy());
            }
        }
    }

    long spLong = SectionPos.asLong(cx, cy, cz);
    if (hadFlags) rs.chunkBoundRenderer.removeSection(spLong);
    else          rs.chunkBoundRenderer.addSection(spLong);
    return true;
}
```

Foxy's replacement is the same logic with the return type corrected. The mapping is exact:
0.8 `false` ↔ 0.9 `0`, and 0.8 `true` ↔ the real bitmask.

```java
private int foxy$updateOnUpload(RenderSection section, BuiltSectionInfo info) {
    boolean hadFlags = section.getFlags() != 0;
    int flags = section.getFlags();
    int result = section.setInfo(info);      // real bitmask, preserved
    if (result == 0) return result;
    if (hadFlags == (section.getFlags() != 0)) return result;
    flags |= section.getFlags();
    if (flags == 0) return result;
    /* ...identical body... */
    return result;
}
```

State it needs:

- `level` — `@Shadow` of Sodium's own `private final ClientLevel level`
- `bottomSectionY` — **recomputed** from `level.getMinY()`, not shadowed. Voxy adds this field
  via its `<init>` injection, but shadowing a field another mixin added is order-dependent and
  brittle; deriving it independently is equivalent and self-contained.
- `cachedChunkPos` / `cachedChunkStatus` — Foxy declares its own. These are a memoization
  cache only, so a second copy is harmless.

Voxy's other three injectors on `RenderSectionManager` (`<init>` TAIL, `onChunkAdded` HEAD,
`onChunkRemoved` HEAD) remain Voxy's, untouched.

### Mixin application order

Foxy's `DefaultChunkRenderer` and `RenderSectionManager` mixins must apply **after** Voxy's,
because both target methods Voxy's mixins add (`doRender`) or call sites inside them. Sponge
Mixin applies lower `priority` values first; Voxy's mixins use the default `1000`, so Foxy's
get `priority = 2000`.

## Instance changes

- Remove `DistantHorizons-3.2.0-b-26.1.2-fabric-neoforge.jar`
- Delete the already-disabled Connector stack: `connector`, `ConnectorExtras`,
  `forgified-fabric-api`, `launchpad`
- Enable `voxy-0.2.16-beta`, `voxy-extra-0.1.7`, `Voxy World Gen V2-26.1.2-2.2.4`
- Add the built `foxy-26.1` jar
- **Sodium, Iris, sodium-extra and reeses-sodium-options all stay at their current versions.**

## Verification

Build gate:

- `./gradlew :26.1:build` compiles
- `./gradlew :26.2:build` still compiles (the shared-source refactor must not regress it)

Runtime gate — launch the instance and confirm from `logs/latest.log`:

- Foxy patches all three jars: `foxy-patched-voxy-*.jar`, `foxy-patched-voxy-extra-*.jar`,
  `foxy-patched-voxyworldgenv2-*.jar`
- `voxy`, `voxy_extra`, `voxyworldgenv2` appear in the mod list
- no mixin apply failures for `client.voxy.mixins.json` or `foxy.mixins.json`
- no `NoSuchMethodError` on `ShaderChunkRenderer.begin`
- `/voxy` registers and `/voxy reload` runs without error

Correctness gate for Break A — the whole reason this design exists. Load a world and check
in-game that animated textures still animate (water, lava, fire, a nether portal) and that
block entities render at distance. A regression here is exactly what a bitmask-preserving
port is meant to prevent, and it will not show up in any log.

Minecraft cannot be launched from the agent environment, so the runtime and correctness gates
are run by the user.

## Risks

- **Break A is a fork of Voxy's logic.** It is reconstructed from bytecode, not source. It
  will need rechecking whenever Voxy or Sodium updates, and it lives in the 26.1 module only.
- **Cross-mixin ordering.** Foxy's mixins depend on Voxy's having applied first. If Sponge
  Mixin's ordering guarantees change, both Break A and Break B fixes fail — loudly, at apply
  time, which is the acceptable direction.
- **Annotation rewriting is Voxy-version-specific.** Break C patches a descriptor string that
  only exists in Voxy 0.2.16. This contradicts Foxy's "nothing about Voxy is hardcoded"
  invariant for the 26.1 module; the rewrite must no-op cleanly if the expected descriptor is
  not found, rather than corrupting a future Voxy build.
